# Модуль 04. Практическая работа: Web API для управления командами (TeamsApi)
## Архитектурные решения, шаблон Repository, DTO, AutoMapper и ReturnResult

---

### Архитектурный разбор компонентов

#### 1. Цепочка обработки запроса и поток данных
В приложении строго реализована разделенная многослойная архитектура:
```text
Клиент (HTTP Request)
       │
       ▼
TeamController
       │
       ├──► ITeamRepository (TeamRepository)
       │           │
       │           ▼
       │     Entity Framework Core (AppDbContext)
       │           │
       │           ▼
       │     База данных SQLite (teams.db)
       │
       └──► AutoMapper (IMapper)
                   │
                   ▼
             Entity (Team) ◄──► DTO (TeamDto)
                   │
                   ▼
             ReturnResult<T>
                   │
                   ▼
Клиент (HTTP Response: 200 OK / 201 Created / 404 Not Found)
```

#### 2. Зачем нужен DTO (Data Transfer Object)?
* **Сокрытие внутренних данных:** В сущности `Team` есть поле `Description` (подробное служебное описание). В `TeamDto` это поле отсутствует. Клиент получает только ту информацию, которая ему действительно необходима (`Id`, `Name`, `City`).
* **Защита от Overposting / Mass Assignment:** Клиент не может случайно или злонамеренно перезаписать внутренние поля сущности, которых нет в DTO.
* **Оптимизация сетевого трафика:** Передаются только необходимые поля, снижая нагрузку на сеть.
* **Версионирование контракта:** Внутренняя схема БД может изменяться, не ломая внешний API-контракт для фронтенда.

#### 3. Шаблон Repository (Репозиторий)
* `ITeamRepository` абстрагирует операции с коллекцией команд.
* Контроллер `TeamController` не знает, как именно хранятся данные (в SQLite, SQL Server или в памяти) и не вызывает `AppDbContext` напрямую.
* Это позволяет легко протестировать контроллер с помощью Fake/Mock-репозиториев в Unit-тестах без создания базы данных.

#### 4. Роль AutoMapper
AutoMapper автоматически копирует значения свойств между несовпадающими типами (`Team` и `TeamDto`) по совпадению имен:
```csharp
CreateMap<Team, TeamDto>().ReverseMap();
```
Это исключает необходимость писать бойлерплейт-код вручную:
```csharp
// БЕЗ AutoMapper пришлось бы писать для каждого метода:
var dto = new TeamDto { Id = team.Id, Name = team.Name, City = team.City };
```

#### 5. Единый формат ответа `ReturnResult<T>`
Вместо возврата «сырых» объектов или строк ошибок, все endpoints возвращают стандартизированную структуру:
```json
{
  "isSuccess": true,
  "result": {
    "id": 1,
    "name": "Астана",
    "city": "Астана"
  },
  "errorMessage": []
}
```
* Фронтенд-разработчикам достаточно проверить одно поле `isSuccess`.
* При ошибках (`isSuccess = false`) в массиве `errorMessage` содержится список понятных сообщений для пользователя.
* При этом стандартные HTTP статус-коды (`200 OK`, `201 Created`, `400 Bad Request`, `404 Not Found`) полностью сохраняются.

### Ответы на контрольные вопросы

#### 1. Что такое Entity в Entity Framework Core?
**Entity (сущность)** — это C#-класс, представляющий таблицу в базе данных. Экземпляр сущности соответствует строке таблицы, а свойства класса — колонкам. Сущности отслеживаются контекстом `DbContext` (Change Tracker) для генерации SQL-команд INSERT, UPDATE, DELETE.

#### 2. Для чего используется DTO?
DTO (Data Transfer Object) используется для передачи данных между слоями приложения и клиентом по сети без бизнес-логики. Он защищает внутреннюю модель базы данных, предотвращает уязвимости массового присвоения (Overposting) и оптимизирует объем передаваемых данных.

#### 3. В чем отличие `DbContext` от `Repository`?
* `DbContext` — это реализация паттернов Unit of Work и Identity Map от Microsoft в составе EF Core. Он управляет соединением с БД, отслеживанием изменений и транзакциями.
* `Repository` — это архитектурный шаблон уровня приложения, который абстрагирует конкретную реализацию ORM и предоставляет коллекции предметной области (например, `ITeamRepository`), скрывая детали работы с SQL или EF Core от контроллеров.

#### 4. Что делает метод `ReverseMap()` в AutoMapper?
Метод `ReverseMap()` автоматически создает двустороннее сопоставление (двунаправленный маппинг): не только из источника в приемник (`Team` -> `TeamDto`), но и в обратном направлении (`TeamDto` -> `Team`).

#### 5. Почему единый формат ответа `ReturnResult` удобнее возврата сырых данных?
Он унифицирует клиентскую обработку: клиенту не нужно угадывать, в каком формате придет ошибка или ответ, а наличие общего флага `isSuccess` и массива `errorMessage` упрощает создание переиспользуемых обработчиков на стороне UI.
